# Playbook: nodeflow

Analysis advice and lessons learned for clients whose artifacts are **JSON definitions of visual flows** — node-and-transition graphs exported from a visual flow / IVR / orchestration builder. The consuming skill uses this as guidance while analyzing the artifacts; the KB that gets generated is Claude's composition for *this* client, not a copy of this file.

## When this playbook applies (recognition signals)

Structural signals at the archetype level — vendor-agnostic by design. Specific vendor fingerprints (engine identifier strings, top-level container key names, exact node-type lists) are NOT here; they get captured from the actual artifacts during analysis.

- **File format**: JSON.
- **A node collection and a transition collection.** The JSON contains (under some top-level container) a list or map of *nodes* and a separate list or map of *transitions* / edges wiring nodes together. Names vary by vendor — what matters is the structural pair.
- **Each node carries a stable identifier** (commonly UUID) and a **type label** that categorizes its behavior (play / prompt, digit / input collection, script, stop, transfer / dial, etc.). Nodes often also carry an `alias` or `kind` namespaced string, plus attributes and events.
- **Each transition references nodes by ID** — typically a source node + event name → target node, optionally guarded by a condition.
- **Embedded scripts may live inside node attributes.** Short code blocks (a script attribute, pre/post hooks, or condition expressions) usually run in a **sandboxed interpreter**, not general Node/browser JS.
- **Conditions, variables, and child / sub-flows** are often kept in dedicated top-level maps alongside nodes and transitions.
- **Layout coordinates** on nodes and waypoints on transitions are common. They don't change **runtime** behaviour, but they are typically **load-bearing for the editor to import and render** — a missing node coordinate or an empty waypoint set crashes the builder's canvas. Treat "no execution effect" as "no *runtime* effect," never "safe to omit."
- Optional: a fixed engine/runtime fingerprint string identifying the script interpreter. If present, it's a strong vendor-specific recognition signal — capture into the KB, not here.

If a file doesn't match these structural signals (it's an n8n workflow with a `connections` map and no node-type concept, a prose document, a REST API schema, etc.), the playbook doesn't apply.

## The analyst's real job: close the sample-to-platform gap

**A handful of sample flows is not a spec of the platform — it is a few traversals of it.** Each flow exercises only the node types, attributes, events, variables, and patterns it happened to need. But the KB's job is to let a downstream agent **generate new, valid flows** — which means it must describe the *whole platform surface*, not the slice the samples walked.

So sort every fact into one of two buckets and act on the bucket:

1. **Sample-extractable** — the JSON *shapes* and the observed *instances*. Mine these exhaustively from the corpus (next section). They are a **floor**, never the library.
2. **Not sample-extractable** — defaults, full vocabularies, conventions, best-practices, runtime behavior, the rules that make a flow *valid* rather than merely *well-formed*. These are invisible, partial, or unreliable in samples. **Every one must be closed — by requesting a platform artifact (best) or asking the operator/SME (for what no export contains). Never cap the KB at the bucket-1 slice and call it done.**

The operating rule that keeps this honest: **for every must-elicit category below, the row must resolve to an artifact request and/or a tagged question.** A category with no closing mechanism is a silent cap — the single most common failure of this archetype. The generator then emits flows that are structurally plausible but invalid, because it never knew the node type, the default attribute, the injected variable, the routing convention, or the house pattern that no sample exercised.

### What samples CAN reveal — mine these exhaustively

Extraction technique for bucket 1. In every case: **capture exhaustively what the corpus shows, AND log where it only shows a slice** so the gap carries forward to the artifact-request / question round.

- The **JSON envelope, node, transition, condition, and variable *shapes*** (the universal fields each carries), the **variable-binding form** (capture it **wire-complete** — including any discriminator/metadata the binding object carries, e.g. a class/type discriminator on the bound-variable object — not just the logical name→attribute pair, which is what prose tends to show), and where **coordinates** live. Capture the top-level container shape, fixed constants, and universal node fields once.
- **Every distinct node `type` / `alias` / `kind`** across all files, with occurrence counts and source files — then treat that set as a **floor, not the library**. Record the `alias` / `kind` → `type` mapping (and any dual discriminator, e.g. a namespaced alias *and* a PascalCase `type`); aliases are often the handle the runtime dispatches on.
- **Every event name verbatim** from both nodes (their event list) and transitions (their source-event field). Case-sensitive dispatch strings — quote them exactly everywhere downstream.
- **Every script body** in every script-accepting attribute: pull the bare identifiers used as calls/variables (what the runtime actually provides — never assume Node/browser globals) and the condition operator set / function calls the expression language uses.
- **Spot sentinel target IDs** (a literal keyword used as a transition target instead of a real node id) so the generator doesn't dereference them.
- **Check cross-corpus consistency** — a convention that holds in one sample may not be universal; flag discrepancies.
- **Reason over whole flows, not isolated nodes**, to surface scaffolding, singletons, forbidden-in-subflow rules, and required terminal sub-sequences — none of which any single node declares. **Spot recursive / self-referential containers and pin the artifact boundary** (see the table). If a self-nesting container is `null`/empty in the samples, that is a **coverage** fact, not a **fixed-value** fact — find a sample with children, consult the export, or ask; never freeze it to a fixed empty/`null` scalar.

### What samples CANNOT reveal — elicit every row

Walk this table for every nodeflow client. For each row decide whether the corpus actually settles it; if not, close it via the **How to close it** column — request the artifact, ask the tagged question, or both. The tags map to the question bank below (B = BLOCKING, I = IMPORTANT, V = VERIFY ASSUMPTION).

| Knowledge category | What a sample shows | What's missing — and must be elicited | How to close it |
|---|---|---|---|
| **Node palette** | only the types those flows used | the full type vocabulary the builder offers | → palette export · Q-B |
| **Per-node attribute schema** | only the attributes a flow *populated* | every attribute, its type, **default value**, and whether each field is fixed / set-from-input / generated-at-runtime | → node-template export · Q-B |
| **Event & port catalog** | only events that got wired | the complete event list per node type, and the fixed source/target **port identifiers** (often must be used verbatim, never guessed) | → node-template export · Q-B |
| **Platform-injected variables** | **nothing** — they're never declared in a flow's variable map | the global/runtime variables the engine provides for free (caller id, call result, disposition, timings…), their enums, and the rule that flows must NOT re-declare them | → global-variable reference · Q-B |
| **Graph-integrity & id rules** | ids that happen to work in that instance | which ids are **newly generated** vs **copied verbatim**; uniqueness invariants (unique source-port per node, globally-unique condition names + any length cap); whether self-loops are illegal **and any exception** (e.g. a self-referential entry-marker transition the start node must carry); the **sentinel entry port** every node must carry (e.g. an empty-name event) to be reachable, **and whether that entry port's own transition field must be non-null on *every* node** — in attested flows each node's entry event references its inbound transition id (the id is *shared*: it appears on both the source event's outgoing slot and the target's entry slot), so leaving entry slots null on every non-start node passes a naive "is it wired" check yet crashes import when the builder builds the entry port from a null link ref; and whether **every event must be wired / no node may be unreachable** | → validator/convention docs · known-good flow · Q-I |
| **Script runtime & authoring conventions** | only the built-ins a script happened to call, and one way a body was written | the full sandbox API (allowed calls, explicitly forbidden calls, guaranteed built-ins) **and** the mandatory authoring skeleton: required `try/catch` wrap, any declaration line, that code lives in the value field with the binding nulled, per-attribute error fields, and the cross-flow tracking variable every script must update | → scripting API + convention docs · Q-I |
| **Variable-scope & init discipline** | the variables a flow declared | the rule for *which* variables a flow may declare (often: only those used in **this** flow, nothing inherited across parent/child), which node types **never** get variables, the init convention and parent-vs-child differences, naming scheme, and any **auto-derived companion variables** (e.g. a count the engine derives from a collection-valued result) | → convention docs · Q-I, Q-V |
| **Node runtime behavior & return shapes** | the node's static structure | what each node **does** at runtime, the **shape it returns** that downstream scripts branch on (e.g. an availability snapshot, a wait-time object), and behavioral **quirks** (special-key handling, value persistence + auto-cleanup, scope levels) | → node/SME docs · Q-I |
| **Terminal & failure routing** | one instance of where an error / exhausted / failure port went | the *convention*: where each such port must route, per node type, and any success↔failure **mirror** rules | → convention docs · Q-I |
| **Mandatory vs optional sub-flows & default patterns** | the patterns those flows happened to use | the house **default patterns and best-practices** every flow should follow, which sub-flows the agent must emit **by default** vs only on request, and each canonical one's exact internal node sequence | → default-patterns catalog · Q-I |
| **Artifact boundary & self-nesting** | a parent that *references* sub-flows by id, or a sub-flow shown standalone | whether the whole graph is **one** artifact with sub-flows **nested** under a recursive container, or separate linked files — and which container holds the nested definitions | → node-template export / SME · Q-I |
| **Child-flow reference & return contract** | a parent node pointing at a child id | which **per-node attribute** nests the child's definition and whether it **differs by node type**, every **back-reference location** that must agree for import to succeed, and the child stop-node **return-status** semantics (e.g. one status keeps the caller queued, another completes) | → child-flow guide / SME · Q-I |
| **Data/query libraries & provider constants** | a query string only if a flow embedded one | the standard query/template library the DB-backed nodes embed (plus just enough schema to parameterize them), and the data-provider constant each node type uses (and when it switches) | → query/template library · Q-I |
| **Singletons & placement rules** | individual nodes | which node types must be a single shared instance, which are forbidden inside sub-flows, what scaffolding (e.g. a required terminal set) every flow must include | → convention docs · Q-I |
| **Identity / discriminator requirements** | the metadata a flow serialized | which discriminator / class-name fields or metadata objects are mandatory (on **bound-variable objects**, transition labels, node/link models), and what breaks if omitted (e.g. editor import — a model-factory lookup keyed on the missing discriminator throws and the flow won't deserialize); **diff against a known-good flow, since prose routinely omits these** | → node-template export / known-good flow · Q-I |
| **Condition / expression language** | the one or two operators those flows used | the full operator/function set and value-formatting rules (e.g. compare collected digits as strings, copy exact literals from the script — no synonyms/translations) | → scripting docs · Q-I |
| **Envelope enums & constants** | the one or two enum values those flows used | the full flow-type enum, the fixed engine constants, the default sentinel values | → node-template export / SME · Q-I |
| **Layout convention** | the coordinates as rendered | the directional / swimlane rule the coordinates follow, **and the render-load-bearing exacts the importer/renderer require** — node coordinates, the precise **waypoint count** per transition (not just "non-empty"), the **per-transition rendering-flag values** (e.g. a visibility flag, a default-edge flag), and any **start-node entry-marker transition** — no runtime effect, but a wrong count/flag or a missing marker still crashes import/render with a null-dereference | → SME / known-good flow · Q-V |

### When a known-good flow is available, validate the docs against it

Docs — even the builder's own schema export — describe the artifact at the level they choose, and that level is usually **above the serialization layer the importer actually deserializes.** Prose routinely reduces a model object to its *logical* fields and silently drops the **discriminator/metadata fields the editor's deserializer requires** — a class-name discriminator on a bound-variable object or a transition label, a model `type`, a renderer key. That produces the signature silent-invalid of this archetype: the generated flow matches every documented field and the schema check passes, yet the builder throws on import (a model-factory lookup that dereferences `undefined` because the discriminator is missing).

This is not an optional nicety — it is a **mandatory gate**. Every crash in this archetype so far has been a **silent-invalid**: structurally perfect, schema-passing, and rejected by the builder at deserialization. No documented-schema check catches any of them; **only a diff against a known-good flow — and, ideally, an actual import of a generated probe flow — does.** So a known-good flow is a **BLOCKING** input for closing the silent-invalid classes: if the operator has one (or the corpus already contains one), you **must** ground-truth against it before the KB is "done"; if none exists, say so and treat the silent-invalid classes (discriminators, fixed-per-type constants, entry-port wiring, cross-flow references) as **unclosed BLOCKING gaps**, not assumed-fine.

Concretely, whenever even **one** known-good flow exists, make it ground truth and **diff every doc claim against it**:

- For each object kind the docs describe (node, transition, condition, variable, **binding object**, label, child-flow reference, layout point), compare the **exact key-set and discriminator values** of the documented shape against what the attested flow carries. Where the doc shows fewer keys than the flow, **the flow wins** — record the extra fields (especially class-name / `type` / renderer discriminators) as mandatory in the KB.
- **Separate STRUCTURE from VALUES when copying.** Copy an attested object's **shape and discriminators verbatim** (key-set, `_class`/`type`/renderer values, fixed-per-type constants) — a prose example is lossy and drops exactly these. But an object's **reference values are per-instance and MUST be re-pointed, never copied**: any id (`nodeflowId`, variable id, child/sub-flow id, node/port id), any `from.variableName`, any bound-variable `name`. A node-template export in particular ships each attribute **pre-filled with an example binding/child that points at the *template's own* foreign flow/variable/child** — copying those values verbatim carries a dangling cross-flow reference into the output that crashes import (see the "template example values are placeholders" pitfall). Rule to bake into the KB: *copy the shape, re-point every reference.*
- Bake a **mandatory generator verify step** into the KB (its own numbered checklist, e.g. in `06-constraints.md`): after emitting a flow, and **before delivery**, structural-diff it against a known-good flow / the node-template shapes and **reject** on any mismatch. At minimum it must fail the build on each known silent-invalid class: (a) a fixed-per-type constant (data-provider id, discriminator) not equal to an **attested** value; (b) a missing mandatory discriminator (`_class` on a bound-variable/label object, node `type`, renderer key); (c) any node whose entry port's transition slot is null; (d) any reference (`from.nodeflowId`, `from.variableName`, child id, port id, condition id) that does not resolve **within this file**. Same principle as the data-provider rule — validate against the attested set, don't trust that "well-formed" means "valid."

This is the **validation** use of sample flows, distinct from bundling them (see "Sample flows are inputs, not deliverables" below): a known-good flow is an analysis-and-verification input — read to confirm the docs and the generator's output — never shipped inside the KB.

## Close the gap first: artifacts to request

Before — or alongside — the gap-question round, ask whether the operator can share any of these. **One good export or convention doc collapses dozens of questions and is far more reliable than reverse-inference from samples.** Two kinds, both high-value:

**A. Schema exports — what the builder can emit:**

- **The per-node definition / JSON-template export** — the builder's own schema for each node (attributes, types, defaults, field classification, full event list, port ids). *This is the single highest-value artifact; it is most of a deep KB by itself.*
- **The node palette / library export** — the full type vocabulary.
- **The global / runtime variable reference** — the variables the engine injects that never appear in a flow's variable map (plus their enums and any auto-derived companions).
- **The scripting runtime / API reference** — sandbox built-ins, allowed vs forbidden calls, guaranteed language built-ins.
- **The standard query / template library** the DB- or HTTP-backed nodes embed (plus just enough data schema to parameterize them).
- **A broader set of SME-blessed "golden" flows** covering more node types and patterns than the initial corpus — useful as *analysis input* to widen coverage and to validate the generator, **but not bundled into the KB** (see "Sample flows are inputs, not deliverables" below).

**B. Convention / rule documents — the team's own build knowledge (just as valuable, and a schema export will NOT contain it):**

Most of what makes a flow *valid* rather than merely *well-formed* — routing conventions, id/uniqueness rules, the script-authoring skeleton, variable-scope discipline, default patterns, naming — lives in the documents a team uses when building flows **by hand**, not in any builder export. Ask for whichever exist:

- **The internal generation guide / build playbook** — how the team assembles a flow step by step.
- **The validation or linter rule-set** — it encodes the constraints directly (this is frequently the single richest source of routing, id, variable, and script rules).
- **The default-patterns catalog** — the canonical/best-practice flow skeletons (entry gating, queue/agent routing with retry, callback/voicemail, transfer, post-call processing) the team reuses.
- **The child-flow / sub-flow guide** — the nesting + back-reference contract and return-status semantics.
- **The naming / initialization conventions doc**, if separate.

Record every unsampled-but-real type / attribute / event as **known-but-unsampled** (named, no fabricated schema/events) until an artifact or the SME confirms it. Per the gap loop, a *promise* to send any of these is a pending **BLOCKING** dependency — wait for it; don't draft around it and silently cap the vocabulary or the rule set.

When you receive a big reference export (the per-node template map is the usual one), the generator will need to read it directly at generation time — so **bundle it into the KB directory and reference the bundled copy**, never the path it arrived on. A KB that points at an external file the consumer can't see is a broken deliverable (see the skill's self-contained-KB rule).

### Sample flows are inputs, not deliverables — don't save them in the KB

Reference / sample flows are for **analysis** (mining shapes and observed instances) and for **validating** the generator against a known-good flow. They are **not** part of the KB once the platform docs cover the surface. When the platform-docs set is reasonably complete — node-template/schema export, palette, variables/globals reference, transitions, child-flow guide, default-patterns catalog, scripting reference — those docs are the authoritative, sufficient source for the generator to produce valid flows, so **do not bundle the sample flow JSONs into the KB**, and don't have any KB file reference them.

Why not keep them "just in case": saved samples add bulk and a standing consistency liability — a stale, partial, or client-specific flow read at generation time pulls the generator toward **sample-mimicry over the documented rules** — without adding any generative capability the docs don't already provide. This is the mirror image of the bundling rule above: a *schema/convention doc* (e.g. the per-node template map) is authoritative and gets bundled; a *sample flow* is a single traversal and does not.

Bundle a sample only as a **documented last-resort fallback** for a specific gap no doc closes and the sample is the sole evidence for — and even then prefer closing that gap with a convention doc, bundle just the minimal illustrative flow, and log it in the gap file as a known sample-derived inference rather than a rule.

### Presenting the request to the operator

Operators rarely recognize abstract names like "per-node template export" or "injected-variable reference" — but they *do* recognize "our node docs" or "the variables sheet." So render the ask in **their** terms: **one line per entity you actually found in their artifacts** (node, variable, transition, condition, child-flow, pattern, layout), and for each say what the doc would contain in plain language, what you already extracted, and why the gap matters. Present it as **one checklist**, not scattered asks, and make the affordance explicit: **they can point you at files / a folder / a wiki / even a screenshot — they don't have to type the answers.** This is what turns a BLOCKING artifact request from confusing into actionable.

A clear rendering looks like this (fill every row from *this* client's real entities and observed counts — don't ship the placeholders):

| The reference doc I'm asking for | What it contains | What I already have from your flows | Why I need it |
|---|---|---|---|
| **Node reference** (one entry per node type) | every node type, its full attribute list, the builder's **default values**, the complete event list, and the **port ids** | the `{N}` node types your samples used, with values as they appeared | to generate *any* node with real defaults — not just the slice your samples walked |
| **Variables reference** | the global/system variables the engine **injects**, their allowed values, and whether a flow may declare them | scripts read `{observed_globals}`, but I can't tell which are injected | so the generator references caller-id / disposition correctly and never wrongly re-declares them |
| **Transitions / wiring reference** | how events wire to ports, the failure-routing rules, and the id-uniqueness rules | the edge shapes and a few event names | so the wiring imports as *valid*, not merely well-formed |
| **Scripting & condition reference** | the script sandbox API (allowed vs forbidden calls) and the full condition operator set | `{observed_calls}` and operator `{observed_ops}` | so scripts/conditions don't call things the runtime doesn't expose |
| **Child-flow guide** | which attribute nests a child **per node type**, every back-reference location, and the stop-status meaning | `{observed_child_wiring}` | so sub-flows package into one importable artifact |
| **Default-patterns catalog** | the canonical flow skeletons your team reuses, and which are emitted by default | the patterns these `{M}` flows happened to use | so the generator follows house best-practice, not sample-mimicry |
| **Layout convention** | the coordinate rule (no runtime effect, but the editor needs valid coordinates + waypoints to import & render) | coordinates as rendered | to place nodes the way your builder expects — and avoid the empty-coordinate import crash |

Close with the out: *"Hand these over however they exist — a docs folder, exported files, a wiki link, even a screenshot — and I'll read and bundle them. If one genuinely doesn't exist, tell me and I'll proceed on what your samples attest and log the gap."* Keep the severity tags from the question bank (node / variables / scripting docs are BLOCKING; the rest IMPORTANT) so the operator sees which docs actually halt the build. Render only the rows that are still open — if the samples already settled an entity, drop its row rather than asking for a doc you don't need.

## Questions to ask the operator

Ask in **two tiers**. *First*, request the artifacts above — they answer most of this by construction. *Then* interview the operator/SME on the conventions no export contains. This is a phrasing bank, not a checklist: align scope first, then ask only the in-scope unknowns whose answers would change the KB, generated from *this* client's artifacts. Fill the `{...}` placeholders from your analysis; don't enumerate the list verbatim. Every row in the table above should resolve to one of these.

**BLOCKING — coverage the KB cannot be complete without**

- **Node palette completeness (reconcile, don't just count).** "I observed `{observed_types}`. Samples show only the types a flow used — can you share the full palette / node-definition export so I capture the rest, with their attribute schemas, defaults, events, and port ids? Anything in the palette but absent from a sample I'll record as available-but-unsampled rather than guess."
- **Per-node attribute schema & defaults.** "For each node type, what is the complete attribute list with default values, and which fields are fixed vs set-from-input vs generated at runtime? Samples only reveal the attributes a flow happened to populate."
- **Platform-injected variables.** "What global / runtime variables does the engine provide that never appear in a flow's variable map (caller id, call result, disposition, call timings, etc.), and what are their allowed values? The generator must reference these and must NOT re-declare them — and I can't see them in any sample."

**IMPORTANT — conventions samples under-reveal**

- **Default patterns & best practices.** "What are your standard/default flow patterns and the build best-practices every flow should follow — the things your team applies by habit that wouldn't surface as a rule in any single sample? For each canonical sub-flow (entry gating, queue/agent routing with retry, callback/voicemail, recording, transfer, post-call processing), the exact node sequence, and which the agent should emit **by default** vs only when the request asks."
- **Graph-integrity & id rules.** "Which id fields does the generator create fresh (and in what format) vs copy verbatim from the template? What are the uniqueness rules (e.g. one source-port per node, globally-unique condition names, any length cap)? Must every node carry a sentinel entry port to be reachable, must every event be wired, and are self-loops or dangling ports illegal (and does the start/entry node nonetheless require a self-referential entry-marker transition)? These make a flow importable and aren't visible from sample ids."
- **Script runtime & authoring conventions.** "Scripts in the artifacts call `{observed_built_ins}`. What is the full allowed set the runtime provides, and which calls are explicitly forbidden? And beyond the API — is there a required authoring skeleton: a mandatory `try/catch` wrap, a declaration line, where the code must live in the attribute (value field vs binding), per-attribute error fields, and a cross-flow tracking variable every script must update?"
- **Variable-scope & init discipline.** "Is there a rule about *which* variables a flow may declare — only those used in this flow, nothing inherited from parent/child? Which node types never get variables? What's the init convention (where, default values), and how do parent vs child sub-flows differ (values a parent sets that a child must not re-init)? Are there auto-derived companion variables (e.g. a derived count) the engine exposes from a result? Is there an enforced naming scheme, and which node type writes which result variable?"
- **Node runtime behavior & return shapes.** "For each node type, beyond its schema — what does it do at runtime, what does it return that a downstream script branches on (the JSON shape), and does it have behavioral quirks (special-key handling, value persistence with auto-cleanup, scope levels) the generator must account for?"
- **Terminal & failure routing.** "Where must each node's error / exhausted-retries / failure ports route by convention — one designated terminal, a prompt-then-stop, something per node type? And do any failure ports mirror their matching success port's destinations?"
- **Artifact boundary, sub-flow packaging & child contract.** "Is the deliverable a single self-contained file with all sub-flows **nested** under a recursive container, or separate linked artifacts? Which per-node attribute nests a child's full *definition* (and does it differ by node type) vs which merely lists its *id*? What are all the back-reference locations that must agree for import to succeed, and what do the child stop-node return statuses mean? I saw `{container}` empty/`null` in the samples — confirm whether it nests child definitions when children exist."
- **Singletons, placement & scaffolding.** "Any node types that must exist as a single shared instance reused across paths? Any forbidden inside sub-flows? Any required start/init node, terminal set, or closing sub-sequence every flow must include?"
- **Data/query library & provider constants.** "For DB- or HTTP-backed nodes, is there a standard query/template library (and the schema it targets), and what data-provider constant does each node type use — and when does it switch?"
- **Identity / discriminator requirements.** "Which fields or metadata objects are mandatory for a flow to import and run (e.g. class discriminators on bound variables or transition labels, a node `type` distinct from its `alias`), and what fails if they're missing?"
- **Condition / expression language.** "Conditions used `{observed_operators}`. Is that the complete operator/function set, and are there value-formatting rules (e.g. compare collected digits as strings, copy exact values from the script with no synonyms/translation)?"
- **Envelope enums & constants.** "What are the allowed flow-type values, the fixed engine constants, and the default sentinel values for the top-level envelope? Samples only show the one or two we used."
- **Rare node usage.** For a type seen in only one or two files: "I saw `{TypeName}` only in `{filenames}` — standard type or a one-off variant?"

**VERIFY ASSUMPTION — state the default, let them correct**

- **Variable initialization.** "I observed variables initialized in `{init_node_type}` before any node references them — confirm that's the required convention?"
- **Parent vs sub-flow init.** "Do sub-flows re-initialize the same way, or does the parent set values a child must not touch?"
- **Engine fingerprint.** "I saw `{engine_fingerprint}` as the interpreter id — always fixed for this platform, or does it vary by environment/version?"
- **Layout convention.** "Coordinates look like `{observed_layout_rule}` (e.g. left-to-right by flow order, start leftmost / stop rightmost, branches offset vertically). Confirm? (No runtime effect — but the builder still needs valid coordinates to render, so I'll always emit them.)"
- **Render-load-bearing exacts.** "Beyond coordinates: how many waypoints does each transition carry in a valid flow — I see `{observed_count}`; is that exact or just a minimum? What per-transition rendering-flag values (e.g. a visibility flag, a default-edge flag) does each transition class use (uniform, or different for error/default edges)? And does the start/entry node carry a self-referential entry-marker transition the importer needs? A wrong count or flag, or a missing marker, crashes the canvas with a null-dereference even though every field is present, so I'll match what your valid flows attest exactly."

## Common pitfalls

When composing the KB's Critical Rules, draw from these (the ones that apply + new ones the analysis surfaces):

- **Do not mistake the corpus for the platform.** Samples are traversals, not a spec. The KB must cover the whole surface a generator could need, not just the slice the samples walked.
- **Do not skip the artifact request and reverse-infer a schema from samples.** Defaults, field classification, full event/port catalogs, and the injected-variable list are unreliable or impossible to recover from instances — ask for the export.
- **Do not bundle sample/reference flows into the KB when the platform docs cover the surface.** Samples are analysis and validation inputs, not a KB deliverable. With a reasonably complete platform-docs set the docs are authoritative and sufficient to generate valid flows; saved sample JSONs only add bulk and tempt the generator into sample-mimicry over the documented rules. Bundle a sample only as a last-resort, documented fallback for a gap no doc closes — never as the default.
- **Do not skip the *convention* documents.** A schema export tells you the shapes; the routing rules, id/uniqueness contract, script skeleton, variable-scope discipline, and default patterns live in the team's build guide / validation rule-set / pattern catalog. Missing these caps the KB at "well-formed" and never reaches "valid."
- **Do not omit platform-injected variables** just because they never appear in a flow's variable map. They are invisible in samples by definition, and the generator both needs them and must not re-declare them.
- **Do not treat the sample-observed node set as the full palette.** Reconcile against an authoritative palette; record unsampled-but-real types as gaps; never silently cap the vocabulary.
- **Do not cap graph-integrity at "what the sample's ids happened to do."** Which ids are freshly generated vs copied, the uniqueness invariants, the sentinel entry port, the self-loop rule (illegal in general, but the start node may need a self-referential entry-marker transition) and the no-unreachable-node rule — all are invisible until stated, and a flow that violates them fails import even though every value looks plausible.
- **Do not leave the entry port's transition slot null on non-start nodes.** The "every node carries an empty-name entry port" rule is only half of it: in attested flows **every node's entry event also has a non-null transition slot referencing its inbound transition** (the id is *shared* — it sits on both the source event's outgoing slot and the target's entry slot). A generator that wires only the *source* side (outgoing events) and leaves every entry slot null produces a flow where each node looks reachable, passes an "is every named event wired" check, and still crashes import — the builder constructs each node's entry *port* from that link ref and dereferences `undefined`. Rule: after wiring, set each node's entry event's transition to one of its inbound transition ids (the start/entry node, having none, gets a synthetic/self-marker id per the layout rules). Verify: **zero entry events with a null transition slot.** Confirm the exact shape (single ref vs all-inbound) against a known-good flow.
- **Do not copy a per-node template's *example values* as if they were defaults — they are placeholders that reference a FOREIGN flow.** A per-node template/JSON export ships each attribute pre-filled with an illustrative value, and for reference-typed attributes those values point *outside the template*: a variable **binding** whose `from` names another flow's id and a variable that doesn't exist here; a child/sub-flow (`NodeFlow`-typed) attribute holding a **child id from the template's own example** that isn't nested in the flow being generated; pre-baked node/port/child ids. Instantiating a node by deep-copying the template verbatim carries these **dangling cross-flow references** into the output. They survive every schema and value-type check (the shapes are perfect) and then crash import when the builder resolves the reference — a registry/model lookup on a foreign id returns `undefined` and `.getInstance()` throws. Rule: on instantiation, **sanitize every attribute** — clear any inherited binding (`from`/bound-variable object) and any reference-typed child id, then re-establish *only* the bindings and children this flow actually creates, re-pointing `from.<flowId>` to this flow and every child id to a node nested in this file. Verify: **no `from` names a foreign flow id or an undeclared variable, and no reference-typed attribute names a child id absent from this file's nested children.** Only the *classification* and *structure* of a template are authoritative; its example *values* are not.
- **Do not treat the variable map as free-form.** Flows often must declare only the variables they use, never re-declare injected/global or parent-set variables, and skip variables on whole classes of nodes — and the engine may expose auto-derived companions the generator must know about.
- **Do not describe the scripting layer as generic JavaScript, or as API-only.** It is typically a sandboxed interpreter, and there is usually a mandatory authoring skeleton (try/catch wrap, a declaration line, a cross-flow tracking variable, per-attribute error fields) a sample only partially reveals. Built-ins come from real script bodies and the runtime reference, not web/Node assumptions.
- **Do not reduce a node to its schema.** Its runtime behavior, the shape it returns, and its quirks (special-key handling, persistence, scope levels) drive the wiring and scripts around it; capture them, not just its fields.
- **Do not call layout "cosmetic" / "no execution effect" and skip it — and do not generalize its load-bearing minutiae to "present / non-empty."** Coordinates and waypoints don't change runtime behaviour, but the editor's importer and canvas renderer dereference them: a missing node coordinate or an empty transition waypoint collection crashes import/render (a null-dereference deep in the importer/renderer) and the flow never draws. Classify layout as **import/render-load-bearing**. *Node positions* are free, but several layout facts are **exact, not "well-formed-is-enough"** — a value that is structurally present yet wrong still crashes the renderer, so capture each as the exact value known-good flows attest, never a floor like "≥1." In particular: **(a) the waypoint COUNT** per transition — a renderer that dereferences a later waypoint index crashes on a single-waypoint link even though the waypoint collection is non-empty; if every attested transition carries exactly N waypoints, the rule is "exactly N," not "≥1." **(b) the per-transition flag values** (e.g. a visibility flag, a default-edge flag) the renderer assumes, and whether they are uniform across all transitions or differ by class (e.g. error/default edges vs normal). **(c) any entry-marker transition** the start/entry node must carry (often a self-referential empty-event transition) for its entry port to be renderable. Extract these from a known-good flow during analysis (samples are analysis inputs, just not bundled) and from the validator / SME, and record the exact attested values. "No execution effect" is about the *runtime*, never a licence to omit **or to approximate**.
- **Do not paraphrase event names, aliases, or port ids.** They are exact dispatch/identity strings — quote them verbatim everywhere.
- **Do not record error / terminal routing as a free choice when it's a fixed convention.** If the platform mandates where error / exhausted / failure ports go (or that a failure port mirrors its success port), capture it as a rule; "route somewhere sensible" lets the generator emit non-conforming flows.
- **Capture fixed per-type constants from what working flows attest, not from documentation "options."** A node's data-provider id (and similar fixed-per-type strings) is constant per type. Record the value **real working flows actually carry** for each type — including `null` where that's what they use. Be wary of a template/doc that lists several "options" for such a field: an option named only in a comment, attested in **no** working flow, may be unregistered and will crash import (a null-registry read on the unregistered key). In the KB, pin the canonical attested value per type, note that documented-but-unattested alternatives are unverified, and state that the value is copy-verbatim and an unregistered one breaks import — so the generator copies it and can validate against the allowed set (this is the data-provider analogue of the verbatim port-id rule).
- **Do not let a documented *pattern* smuggle an unattested constant into a KB rule.** The trap is second-order: a house pattern from a doc/SME (e.g. "for multi-queue use a single queue-based router node") arrives *with* a specific constant (a data-provider id, a node subtype) that appears in **no** working flow. Writing that pattern into the KB as a positive rule elevates the unattested constant to authoritative — and the KB now actively *tells the generator to emit the thing that crashes import*, contradicting its own attest-only constant rule. Guard: **every constant a pattern references must itself be attested**; if the pattern needs a constant no working flow carries, either re-express the pattern using attested constants (e.g. model multi-queue as N attested per-queue nodes) or hold the pattern as an unverified gap — never bake an unattested constant into a rule just because a pattern narrative used it. Cross-check: no positive KB rule/pattern may reference a constant the KB's own "attested values" table doesn't list.
- **Validate docs and generated output against a known-good flow; an attested object beats a prose example.** Documentation — even a schema export — describes the artifact above the serialization layer and routinely omits the **discriminator/metadata fields the importer deserializes**: a class-name discriminator on a bound-variable or label object, a model `type`, a renderer key. A flow that matches every documented field still crashes import on the missing discriminator (a model-factory lookup that dereferences `undefined`). When a known-good flow exists, **diff every documented object shape against it and copy attested objects (shape + discriminators) verbatim** — re-pointing their reference values per instance — rather than reconstructing from prose, and capture the structural-diff as a generator verify step. Sibling of the data-provider "attest, don't trust doc-options" rule above and the verbatim port-id rule.
- **Do not call a KB "done" for the silent-invalid classes until a generated probe flow round-trips against a known-good flow.** This is the meta-rule the other pitfalls hang off, and the one whose absence is most expensive: reading the docs and matching every field is exactly what produces a flow that passes schema and then throws `getInstance` on import. The silent-invalid classes — unregistered fixed-per-type constants, missing model discriminators (`_class`/`type`/renderer), null entry-port transition slots, dangling cross-flow references copied from template example values — are **individually invisible and collectively fatal**, and each was found only by *importing an actual generated flow* and diffing it against a known-good one. So make it a build gate: **synthesize a small probe flow from the KB, structural-diff it against a known-good flow (and import it if the builder is reachable), and only ship the KB once the probe survives.** If there is no known-good flow to diff against, the KB has **not** closed these classes — request one (BLOCKING) and log the gap; never assume "well-formed" reached "valid." A KB that has never had one of its own outputs validated is unproven precisely where this archetype fails.
- **Do not flatten a recursive container into a fixed scalar, and do not externalise nested sub-flows.** A self-nesting field (a child / sub-flow map) seen as `null` in a sample is empty-by-coverage, not constant. Classifying it "fixed null" makes the generator emit child flows as **separate files** and break the single-artifact contract. Capture the recursive shape *and* the packaging boundary (one file, children nested under the container, `null` only for a leaf) as a constraint.
- **Do not merge variables-and-scripting into the building-blocks file.** The variable system and the expression/script language are a separate subsystem the generator dereferences constantly; give them their own reference.
- **Do not invent node types or attributes.** Document only what the corpus or an authoritative artifact confirms; record absent-but-likely items under Known Gaps without fabricating schema/events.
- **Do not include external REST API / auth / webhook reference.** Producing flow JSON is artifact-emission; the standard *query/template a node embeds* is in scope, but a general API/integration surface is not.
- **Do not hardcode vendor fingerprints into this playbook.** Engine identifier strings, container key names, exact node vocabularies, the injected-variable list — all vary by vendor; they belong in the KB as observed values, not here.

## Typical KB shapes that have worked

Past clients of this archetype have settled around these KB files. Reference only — the file list is sized to what *this* client's artifacts and the elicited platform surface demand.

- `00-overview.md` — Domain context, glossary (node, transition, event, condition, port, variable, child flow), top-level container shape, fixed engine constants, the allowed flow-type enum.
- `01-building-blocks.md` — One subsection per node type (observed and elicited): alias, type, purpose, when-to-use, **full attribute schema with defaults and field classification**, event + port catalog, and the node's **runtime behavior / return shape / quirks**. Universal node fields documented once.
- `02-composition-rules.md` — Transition schema, conditional vs unconditional transitions, condition resolution, source/target port semantics, the **id-generation & graph-integrity rules** (which ids are fresh vs copied, uniqueness invariants, sentinel entry port, no self-loops / no unreachable nodes), parent ↔ child wiring (the reference locations) **plus where a child's full definition is nested**, sentinel target ids, terminal/failure routing conventions and success↔failure mirror rules.
- `03-artifact-schema.md` — Full top-level schema, fields classified fixed / identity / configurable / computed — but a **recursive sub-flow container is structural, not a fixed scalar; never freeze it to `null`** — and the **single-artifact packaging rule** (does the whole graph serialize to one file with sub-flows nested, or separate linked files?), with minimum-valid + fully-featured annotated examples.
- `04-variables-and-scripting.md` — Variable system, **platform-injected/global variables**, **scope & init discipline** (which variables a flow may declare, which nodes never get them, auto-derived companions, parent-vs-child rules), naming conventions, embedded scripting, the **authoring skeleton** (try/catch, declaration, tracking variable, per-attribute error fields), the sandbox API (allowed + forbidden), condition language with CORRECT/WRONG examples.
- `05-patterns.md` — Canonical composition patterns and house best-practices, each with when-to-use, step-by-step node sequence, required wirings, anti-pattern. Mandatory/default patterns and scaffolding sub-flows called out and distinguished from optional ones.
- `06-constraints.md` — Numbered constraints (rule / consequence / CORRECT / WRONG), capturing routing conventions, id/uniqueness & reachability rules, singleton/placement rules, single-artifact packaging (sub-flows nested, not separate files), identity/discriminator requirements, and value-formatting rules. **Must end with a mandatory post-generation verification checklist** — the concrete checks the generator runs and *rejects* on before delivery, one per silent-invalid import-crash class: (a) every fixed-per-type constant (data-provider id, discriminators) equals an **attested** value; (b) every mandatory discriminator present (`_class` on bound-variable/label objects, node `type`, renderer keys); (c) zero null entry-port transition slots; (d) full referential integrity — every id/`from`/child ref resolves **within this file**, no foreign `nodeflowId` or undeclared variable; (e) wiring/routing invariants (every event wired, error→default-stop, failure-mirrors-success, no self-loops, condition-name uniqueness/length). A schema check catches none of these; this checklist is what makes "well-formed" reach "valid."
- `07-layout-rules.md` — Coordinate / waypoint conventions. **Load-bearing for import/render, not runtime:** every node needs integer coordinates; an empty waypoint collection or a missing coordinate crashes the importer/canvas with a null-dereference. Node *positions* are cosmetic, but the render-load-bearing **exacts are not** — record, as the precise values known-good flows attest (not floors like "≥1" / "non-empty"): the **exact waypoint count** per transition ("exactly N," because a renderer that dereferences a later waypoint index crashes on a single-waypoint link), the **per-transition rendering-flag values** (e.g. a visibility flag, a default-edge flag; and whether they're uniform or differ by transition class), and any **entry-marker transition** the start node must carry. A wrong count, a wrong flag, or a missing marker crashes the canvas even though every field is present.
- `08-input-checklist.md` — Per-instance fields the generator must extract before building a flow, tiered by criticality.
- `09-gap-log.md` — Remaining uncertainties, known-but-unsampled node types/attributes/events, and any artifact still pending from the operator.

## Skip-entirely categories

What's typically out of scope. The KB should never emit:

- External REST API reference.
- Authentication setup.
- Webhook contracts.
- Entity data model catalogs (the *standard query/template a node embeds* is in scope; a general data-model reference is not).
- Generic configuration reference.

Generating flow JSON is artifact-emission, not API integration. Including these wastes context and invites the generator to hallucinate a surface the runtime doesn't expose to flow scripts.
