# Exotel - IVR Nodeflow JSON Knowledge Base

## Overview

Exotel's IVR (Interactive Voice Response) Nodeflow is a JSON-based configuration format that defines complete call flows using a node-based architecture. Each nodeflow artifact represents a self-contained IVR application that processes incoming calls through a series of interconnected nodes. Each node performs a specific action (play audio, collect DTMF input, execute scripts, transfer calls, etc.) and transitions to other nodes based on events and conditions.

The nodeflow JSON is interpreted at runtime by Exotel's call processing engine (`nodeflow.script.interpreter.js`). When a call arrives, the engine starts at the designated `startNodeID`, executes that node's logic, evaluates the resulting event, and follows the configured transitions to subsequent nodes until reaching a terminal state (typically the `stopNodeID`).

This format is used to create sophisticated call routing logic without traditional programming, though JavaScript can be embedded in ScriptNodes for custom business logic. The artifact is typically deployed to Exotel's platform where it becomes the active call flow for a specific phone number or inbound route.

## Core Concepts

### Nodeflow

A **nodeflow** is the complete IVR application definition. It contains metadata about the flow itself and an array of all nodes that comprise the call flow. The nodeflow is the top-level container for everything related to a specific IVR application.

Key properties:
- **Unique identifier**: Every nodeflow has a UUID
- **Type designation**: Defines the flow category (e.g., InboundNodeFlow, OutboundNodeFlow)
- **Entry and exit points**: Specified via `startNodeID` and `stopNodeID`
- **Execution context**: The `scriptType` determines the runtime interpreter

### Node

A **node** is a discrete step in the call flow representing a single action or operation. Nodes are the building blocks of the IVR. Each node has:
- A unique ID and human-readable name
- A type that determines its behavior (PlayNode, DigitCollectionNode, ScriptNode, etc.)
- Attributes that configure its specific behavior
- Events that define how it transitions to other nodes
- UI properties for visual rendering in flow designers

Nodes execute in sequence as the call progresses through the flow. The engine processes one node at a time, executing its logic and then transitioning to the next node based on the event that fires.

### Event

An **event** represents an outcome or condition that occurs during node execution. Events are the mechanism for routing between nodes. Each node can define multiple events, each corresponding to a different possible outcome of that node's execution.

Common event patterns:
- **Success/Failure events**: Standard outcomes for most operations
- **Hangup events**: Triggered when the caller disconnects
- **System errors**: Catch-all for unexpected failures
- **Custom events**: Node-type-specific outcomes (e.g., "no.input.collect.digit", "invalid.input.collect.digit")

Events contain transition instructions that tell the engine which node to execute next.

### Transition

A **transition** defines the routing from one node to another when an event fires. There are two types:

- **Unconditional transitions**: Always route to a specific node (specified by node ID)
- **Conditional transitions**: Evaluate an expression and route based on the result

Most events use unconditional transitions. Conditional transitions allow for dynamic routing based on variables, call data, or complex business logic.

### Attribute

An **attribute** is a configuration parameter that controls how a node behaves. Attributes have:
- A name (identifier for the parameter)
- A type (String, Boolean, Long, NodeFlow, etc.)
- A value (static value or reference to a variable)
- UI rendering hints for flow designers

Different node types require different sets of attributes. For example, a PlayNode requires a `promptName` attribute specifying which audio file to play, while a DigitCollectionNode requires attributes like `minDigits`, `maxDigits`, and `timeout`.

### Variable

**Variables** store data during call flow execution. They are declared in ScriptNodes and can be accessed across the entire flow. Variables enable:
- Storing caller input (DTMF digits, speech recognition results)
- Maintaining state across multiple nodes
- Passing data between nodes
- Making routing decisions based on runtime data

Variables are referenced in JavaScript snippets within ScriptNodes and in conditional expressions.

### Sub-flow

A **sub-flow** (or child nodeflow) is a reusable nodeflow that can be invoked from a parent nodeflow. Sub-flows enable:
- Modular IVR design
- Reusable components across multiple flows
- Simplified maintenance of common patterns

Sub-flows are referenced via the `childNodeflow` mechanism in certain attributes.

## Artifact Structure

An Exotel IVR Nodeflow JSON file follows this top-level structure:

```json
{
  "nodeflowInfo": {
    // Metadata and configuration for the entire flow
    "id": "c1a2b3d4-e5f6-7890-1234-567890abcdef",
    "name": "KFC Inbound IVR",
    "description": "Human-readable description of what this flow does",
    "nodeflowType": "InboundNodeFlow",
    "scriptType": "nodeflow.script.interpreter.js",
    "startNodeID": "e8a9b0c1-d2e3-4f5a-6b7c-8d9e0f1a2b3c",
    "stopNodeID": "SuccessStopNode",
    "nodes": [
      // Array of all nodes in the flow
      {
        "id": "unique-node-id",
        "alias": "node.type.identifier",
        "name": "Human Readable Name",
        "type": "NodeType",
        // ... node configuration
        "events": [ /* event definitions */ ],
        "attributes": [ /* attribute definitions */ ]
      }
      // ... more nodes
    ]
  }
}
```

### Top-Level Structure: `nodeflowInfo`

The entire artifact is wrapped in a single `nodeflowInfo` object. This object has two main sections:
1. **Metadata fields**: Properties that describe and configure the flow itself
2. **Nodes array**: The complete collection of nodes that make up the flow

### Metadata Fields

- **`id`** (String, UUID): Unique identifier for this nodeflow across the entire Exotel platform
- **`name`** (String): Human-readable name displayed in dashboards and logs
- **`description`** (String): Detailed explanation of the flow's purpose and behavior
- **`nodeflowType`** (String): Category of the flow (e.g., "InboundNodeFlow", "OutboundNodeFlow")
- **`scriptType`** (String): Runtime interpreter to use (observed value: "nodeflow.script.interpreter.js")
- **`startNodeID`** (String, UUID): The ID of the node where execution begins
- **`stopNodeID`** (String): The ID of the terminal node where the flow ends
- **`nodes`** (Array): Collection of all node definitions

> **Needs Verification:** What other values are valid for `nodeflowType` and `scriptType`? Are there version-specific interpreters?

### Nodes Array

The `nodes` array contains every node in the flow in no particular order. Nodes can reference each other via IDs in their transitions. The execution order is determined by the transition logic, not the array order.

Each node in the array is a complete node definition object (detailed in subsequent sections).

## Node Object

Every node in the `nodes` array shares a common base structure, with type-specific variations in the `attributes` and `events` arrays.

### Common Node Fields

```json
{
  "id": "e8a9b0c1-d2e3-4f5a-6b7c-8d9e0f1a2b3c",           // Unique identifier for this node
  "alias": "node.script",                                  // Type identifier/category
  "name": "StartScript",                                   // Human-readable name
  "type": "ScriptNode",                                    // Node type class
  "isConfigruationsValid": true,                           // Validation flag
  "basePath": null,                                        // Optional base path for resources
  "version": 1,                                            // Node schema version
  "visible": true,                                         // UI visibility flag
  "connectedChildNodeflowId": [],                          // Array of child flow IDs
  "events": [ /* array of event objects */ ],              // Event definitions
  "attributes": [ /* array of attribute objects */ ],      // Configuration attributes
  "uiProps": {                                             // UI rendering properties
    "rendererType": "DefaultNode",
    "customRendererPath": null,
    "x": 0,                                                // X coordinate for visual editor
    "y": 300,                                              // Y coordinate for visual editor
    "style": null,
    "visible": true
  }
}
```

### Field Descriptions

**`id`** (String, UUID, required)
- Unique identifier for this specific node instance
- Must be unique across all nodes in the nodeflow
- Referenced by transitions to route to this node
- Format: UUID (e.g., "e8a9b0c1-d2e3-4f5a-6b7c-8d9e0f1a2b3c")

**`alias`** (String, required)
- Type identifier that categorizes the node
- Observed values: "node.script", "node.play", "node.digit.collection", "node.transfer", "node.invoke.nodeflow"
- Appears to follow pattern: `node.<action-type>`
- Used for node type registration and rendering

**`name`** (String, required)
- Human-readable label for the node
- Displayed in visual flow designers and logs
- Should be descriptive of the node's purpose
- Examples: "StartScript", "Welcome", "LanguageSelection", "TransferToAgent"

**`type`** (String, required)
- Class name of the node type
- Observed values: "ScriptNode", "PlayNode", "DigitCollectionNode", "TransferNode", "InvokeNodeFlowNode", "StopNode"
- Determines which attributes and events are valid for this node

**`isConfigruationsValid`** (Boolean, required)
- Validation status of the node's configuration
- Note: Field name appears to have a typo ("Configruations" vs "Configurations")
- When `true`, the node's configuration has passed validation
- When `false`, there are validation errors that must be resolved

> **Needs Verification:** What validation rules are applied? Is this flag set by the platform or manually by users?

**`basePath`** (String or null, optional)
- Base path for resolving resource references
- Observed value: `null` in all sample nodes
- Likely used for audio file paths or external resource references

**`version`** (Integer, required)
- Schema version for the node structure
- Observed value: `1` in all samples
- Allows for backward-compatible schema evolution

**`visible`** (Boolean, required)
- Controls visibility in UI editors
- When `true`, node appears in visual flow designer
- When `false`, node is hidden (possibly for deprecated or internal nodes)

**`connectedChildNodeflowId`** (Array of Strings, required)
- Array of child nodeflow IDs that are invoked from this node
- Empty array `[]` when no child flows are used
- Populated when using InvokeNodeFlowNode to call sub-flows
- Each element is a UUID of another nodeflow

**`events`** (Array of Event objects, required)
- Collection of all possible events this node can emit
- Each event defines routing logic to other nodes
- Minimum one event (typically an unnamed default event)
- See "Event Object" section for detailed structure

**`attributes`** (Array of Attribute objects, required)
- Configuration parameters specific to this node type
- Each attribute has a name, type, and value
- Required attributes vary by node type
- See "Attribute Object" section for detailed structure

**`uiProps`** (Object, required)
- Properties for visual rendering in flow designers
- Contains positioning, styling, and rendering hints
- See "UIProps Object" section for detailed structure

## Event Object

Events define the possible outcomes of a node's execution and how the flow should proceed for each outcome. Every node has at least one event.

### Event Structure

```json
{
  "name": "success.collect.digit",                         // Event identifier
  "unconditionalTransition": "9e1c6a2f-d35b-4c7e-a69a-0b1c2d3e4f5a",  // Target node ID
  "conditionalTransitions": [],                            // Array of conditional transitions
  "uiProps": {                                             // UI rendering properties
    "rendererType": null,
    "customRendererPath": null,
    "style": null,
    "defaultFailureTransition": false,                     // Marks default error handler
    "visible": true,                                       // UI visibility
    "behavesAs": null,
    "id": "a6b7c8d9-e0f1-2345-6789-0abcdef01234"          // Event instance ID
  }
}
```

### Event Field Descriptions

**`name`** (String, required but can be empty)
- Identifier for the event type
- Empty string `""` typically represents the default/primary event
- Named events indicate specific outcomes (e.g., "success.collect.digit", "hungup.collect.digit", "invalid.input.collect.digit")
- Event names follow pattern: `<outcome>.<action>.<context>`

**`unconditionalTransition`** (String or null, required)
- Node ID to transition to when this event fires
- Must be a valid node ID that exists in the `nodes` array
- When `null`, no transition occurs (flow may terminate)
- Used for simple, deterministic routing

**`conditionalTransitions`** (Array, required)
- Array of conditional transition objects
- Each conditional transition evaluates an expression and routes based on the result
- Processed in order; first matching condition wins
- Empty array `[]` means no conditional logic (relies on unconditionalTransition)

### Conditional Transition Structure

```json
{
  "expression": "languageInput == '1'",                    // JavaScript expression
  "transition": "target-node-id-here"                      // Node ID if expression is true
}
```

### Event UIProps

**`rendererType`** (String or null)
- Specifies custom rendering for this event in visual editors
- Observed value: `null` in most cases

**`customRendererPath`** (String or null)
- Path to custom renderer component
- Observed value: `null` in all samples

**`style`** (String or null)
- Custom CSS or styling information
- Observed value: `null` in all samples

**`defaultFailureTransition`** (Boolean, required)
- Marks this event as the default error handler
- When `true`, this event is used for unexpected failures
- Typically used with "system.error" events
- Can also be `false` for explicit failure events like "failure.collect.digit"

**`visible`** (Boolean, required)
- Controls visibility in visual flow designers
- When `false`, event is hidden (typically for system/error events)
- When `true`, event appears as a connection point in the UI

**`behavesAs`** (String or null)
- Behavioral hint for the event
- Observed value: `null` in all samples
- Likely used for grouping similar events or special handling

**`id`** (String, UUID, required)
- Unique identifier for this event instance
- Different from the node ID and the event name
- Used for tracking and referencing in the UI

**Default/Primary Event** (empty name):
```json

  "unconditionalTransition": "next-node-id",
  "conditionalTransitions": [],

    "defaultFailureTransition": null,
```

```json
    "defaultFailureTransition": false,  // Sometimes true
```

## Node Type: ScriptNode

ScriptNodes execute JavaScript code to perform custom logic, manipulate variables, and make decisions. They are the primary mechanism for adding custom business logic to a flow.

**Type identifier**: `"type": "ScriptNode"`, `"alias": "node.script"`

### ScriptNode Events

ScriptNodes typically define four events:

1. **Default Event** (`name: ""`):
   - Fires immediately when the node is entered
   - Usually transitions to the first script execution or next node

2. **Success Event** (`name: "script.node.success"`):
   - Fires when the script executes without throwing exceptions
   - Normal execution path

3. **Failure Event** (`name: "script.node.failure"`):
   - Fires when the script throws an exception or returns an error
   - Error handling path
   - Often has `"defaultFailureTransition": true`
   - Often has `"visible": false`

4. **System Error Event** (`name: "system.error"`):
   - Catch-all for unexpected system-level errors
   - Always has `"defaultFailureTransition": true`
   - Always has `"visible": false`

### ScriptNode Attributes

**`script`** (String, required)
- JavaScript code to execute
- Has access to `env` object for logging and platform interaction
- Has access to all flow variables
- Common pattern: Declare variables, perform logic, handle errors

```json
{
  "name": "script",
  "type": "String",
  "staticValue": "var env;\nvar dstPhone = '';\nvar hangupAt = '';\ntry {\n  env.info('StartScript: Initializing flow variables.');\n} catch (e) {\n  env.info('Error in StartScript: ' + e.message);\n}",
  "scriptErrors": [],
  "uiProps": {
    "rendererType": "ScriptTypeAttribute"
  }
}
```

**`playSequenceNodeflow`** (NodeFlow, optional)
- Reference to a nodeflow for playing audio sequences
- Typically `null` or not used
- Type: "NodeFlow"

**`dataProviderType`** (String, optional)
- Specifies the data provider for the script
- Typically `null` for simple scripts
- Rendered as "SingleSelectAttributeWidget"

**`postScript`** (String, optional)
- JavaScript code executed after the main script
- Same capabilities as `script`
- Often `null`

```json
{
  "name": "postScript",
  "type": "String",
  "staticValue": "var env;\ntry {\n  env.info('Post-script logic');\n} catch (e) {\n  env.info('Error: ' + e.message);\n}",
  "scriptErrors": [],
  "uiProps": {
    "rendererType": "ScriptTypeAttribute"
  }
}
```

**`preScript`** (String, optional)
- JavaScript code executed before the main script
- Same capabilities as `script`
- Often `null`

### ScriptNode JavaScript Environment

Scripts have access to:
- **`env`** object: Platform API for logging and system interaction
  - `env.info(message)`: Log informational messages
  - Other methods unclear from samples

- **Flow variables**: All variables declared in the flow
  - Variables persist across nodes
  - Common pattern: Initialize in StartScript, use throughout flow

- **Standard JavaScript**: Basic language features (var, try/catch, operators, etc.)

## Node Type: PlayNode

PlayNodes play audio files to the caller. They are used for greetings, prompts, messages, and any pre-recorded audio.

**Type identifier**: `"type": "PlayNode"`, `"alias": "node.play"`

### PlayNode Events

PlayNodes typically define five events:

1. **Default Event** (`name: ""`):
   - Fires immediately when the node is entered
   - Usually transitions to start playing audio

2. **Success Event** (`name: "success.listen.voice.log"`):
   - Fires when audio playback completes successfully
   - Normal completion path

3. **Hungup Event** (`name: "hungup.listen.voice.log"`):
   - Fires if caller hangs up during playback
   - Should route to hangup handler or stop node

4. **Failure Event** (`name: "failure.listen.voice.log"`):
   - Fires if audio playback fails (file not found, format error, etc.)
   - Error handling path

5. **System Error Event** (`name: "system.error"`):
   - Catch-all for unexpected errors
   - Has `"defaultFailureTransition": true`
   - Has `"visible": false`

## Node Type: DigitCollectionNode

DigitCollectionNodes play a prompt and collect DTMF (touch-tone) input from the caller. They are the primary mechanism for menu navigation and user input collection.

**Type identifier**: `"type": "DigitCollectionNode"`, `"alias": "node.digit.collection"`

### DigitCollectionNode Events

DigitCollectionNodes can define up to nine events, covering various input scenarios:

1. **Default Event** (`name: ""`):
   - Fires when the node is entered
   - Begins prompt playback and digit collection

2. **Hungup Event** (`name: "hungup.collect.digit"`):
   - Fires if caller hangs up during prompt or input collection

3. **Success Event** (`name: "success.collect.digit"`):
   - Fires when valid input is collected successfully
   - Often has conditional transitions to route based on collected digits

4. **Failure Event** (`name: "failure.collect.digit"`):
   - Fires when input collection fails (general failure)

5. **Max Retries Exceeded Event** (`name: "max.retry.attempts.exceeded"`):
   - Fires when the maximum number of retry attempts is reached
   - Typically routes to error handler or operator transfer

6. **No Input Event** (`name: "no.input.collect.digit"`):
   - Fires when timeout occurs with no digits entered
   - Triggers retry or "no input" prompt

7. **Invalid Input Event** (`name: "invalid.input.collect.digit"`):
   - Fires when input doesn't match validation rules
   - Triggers retry or "invalid input" prompt

8. **Match Not Found Event** (`name: "match.not.found.collect.digit"`):
   - Fires when input is valid format but doesn't match expected values
   - Different from invalid input (format vs. value mismatch)

9. **System Error Event** (`name: "system.error"`):
   - Catch-all for unexpected errors
   - Has `"defaultFailureTransition": true`
   - Has `"visible": false`

## Validation Rules and Constraints

### Nodeflow-Level Rules

**Unique nodeflow ID**:
- The `id` field in `nodeflowInfo` must be a valid UUID
- Must be unique across all nodeflows in the platform
- Violation: Deployment will fail or overwrite existing nodeflow

**Valid nodeflowType**:
- Must be one of the recognized types (e.g., "InboundNodeFlow", "OutboundNodeFlow")
- Observed value: "InboundNodeFlow"
- Violation: Runtime may not know how to process the flow

**Valid scriptType**:
- Must be a recognized interpreter (e.g., "nodeflow.script.interpreter.js")
- Violation: Flow cannot be executed

**startNodeID must reference existing node**:
- The `startNodeID` must match the `id` of a node in the `nodes` array
- Violation: Flow cannot start; execution fails immediately

**stopNodeID must be valid**:
- The `stopNodeID` must reference a valid stop condition
- Observed value: "SuccessStopNode" (symbolic or actual node ID)
- Violation: Flow may not terminate properly

### Node-Level Rules

**Unique node IDs**:
- Every node's `id` field must be unique within the `nodes` array
- Violation: Transitions will be ambiguous; behavior undefined

**Type and alias must match**:
- The `type` field must correspond to the `alias` convention
- Example: `type: "ScriptNode"` should have `alias: "node.script"`
- Violation: Rendering and validation may fail

**Required attributes per node type**:
- Each node type has a specific set of required attributes
- Missing required attributes will fail validation
- `isConfigruationsValid` will be `false`

**Valid event names per node type**:
- Event names must be recognized for the node type
- Unknown event names may be ignored or cause errors

**connectedChildNodeflowId consistency**:
- If a node invokes child flows, their IDs must be in this array
- Violation: Child flow tracking breaks

### Event-Level Rules

**Valid unconditionalTransition targets**:
- Every `unconditionalTransition` that is not `null` must reference a node ID in the `nodes` array or a valid symbolic ID (like "SuccessStopNode")
- Violation: Flow will break at that transition; call will drop or error

**Conditional transitions must have valid expressions**:
- The `expression` field must be valid JavaScript
- Must reference variables that exist in the flow
- Violation: Runtime error when evaluating the condition

**At least one event per node**:
- Every node must have at least one event (typically the default event)
- Violation: Node cannot transition; flow gets stuck

**defaultFailureTransition uniqueness**:
- Only one event per node should have `defaultFailureTransition: true`
- This is the catch-all error handler
- Violation: Ambiguous error handling

### Attribute-Level Rules

**Type consistency**:
- `staticValue` must be compatible with the `type` field
- Boolean types: "true" or "false" (strings)
- Long types: numeric strings (e.g., "60000")
- String types: any string value
- Violation: Runtime type coercion may fail

**Required attributes present**:
- Node type dictates which attributes are required
- For example, PlayNode requires `promptName`, `timeout`, `dataProviderType`
- Violation: `isConfigruationsValid` will be `false`; node may not execute

**Script syntax validity**:
- JavaScript in `script`, `preScript`, `postScript` must be syntactically valid
- Errors populate the `scriptErrors` array
- Violation: Script execution fails; node fails

**Variable references must exist**:
- Variables in `outputVariable`, conditional expressions, and scripts must be declared
- Typically declared in ScriptNodes before use
- Violation: Runtime error (undefined variable)

**Prompt names must reference existing prompts**:
- All `promptName`, `invalidInputPromptName`, `noInputPromptName` values must exist in the platform's audio library
- Violation: Playback fails; silence or error message played

### Cross-Node Rules

**No orphaned nodes**:
- Every node except the start node should be reachable via some transition path
- Unreachable nodes are not technically invalid but suggest design issues

**No circular loops without exit**:
- Loops (e.g., retry mechanisms) must have a way to exit (max retries, valid input, etc.)
- Violation: Infinite loop; call never terminates

**Hangup events should route to terminal nodes**:
- Hangup events should transition to stop nodes or hangup handlers
- Violation: Flow may attempt to continue after caller has disconnected

### Timing and Timeout Rules

**Timeouts must be positive**:
- All `timeout` attribute values must be > 0
- Violation: Immediate timeout or undefined behavior

**Reasonable timeout values**:
- Timeouts should be appropriate for the action (e.g., 5-30 seconds for digit collection)
- Extremely long timeouts (>5 minutes) may cause resource issues

**Retry limits should be reasonable**:
- `retries` attribute should be 1-5 typically
- Zero retries means no second chance
- Excessive retries (>10) annoy callers and waste resources

## Dependencies and Ordering

### Execution Flow Dependencies

**Start node must be first**:
- The node referenced by `startNodeID` is the entry point
- All other nodes are reached via transitions from this node

**Variables must be declared before use**:
1. Variables are typically declared in an initial ScriptNode (often the start node)
2. Example: `var dstPhone = ''; var languageInput = '';`
3. Subsequent nodes can reference these variables in scripts, conditional expressions, and `outputVariable` attributes

**Prompts must be uploaded before referencing**:
- All audio files referenced in `promptName` attributes must exist in the platform
- This is an external dependency, not enforced in the JSON structure

### Node Ordering in JSON

**Nodes array order is irrelevant**:
- Nodes in the `nodes` array can appear in any order
- Execution order is determined solely by transitions
- Best practice: Order nodes logically (e.g., start to finish) for human readability

### Transition Dependencies

**Target nodes must exist before creating transitions**:
- When creating a new nodeflow, you can either:
  1. Create all nodes first with placeholder transitions, then update transitions
  2. Create nodes in execution order, referencing IDs of already-created nodes

**Conditional transitions evaluated in order**:
- Within an event's `conditionalTransitions` array, conditions are evaluated sequentially
- First matching condition wins
- Order matters if conditions overlap

### Child Nodeflow Dependencies

**Child flows must exist before invocation**:
- When using InvokeNodeFlowNode, the child nodeflow must already be deployed
- The child's ID must be in the parent's `connectedChildNodeflowId` array

**Circular references forbidden**:
- Parent flow cannot invoke itself (directly or indirectly)
- Example: Flow A invokes Flow B, Flow B invokes Flow A = circular dependency
- Violation: Infinite recursion; call resources exhausted

**Variables persist for call duration**:
- Variables declared in ScriptNodes exist for the entire call
- They persist across node transitions
- They are accessible in any subsequent node's scripts and conditions

## Integration Checklist

Follow these steps to create a complete, valid nodeflow JSON:

### Step 1: Define Flow Metadata
- [ ] Generate a unique UUID for `nodeflowInfo.id`
- [ ] Set a descriptive `name` (e.g., "Customer Support IVR")
- [ ] Write a detailed `description` explaining the flow's purpose
- [ ] Set `nodeflowType` to "InboundNodeFlow" (or appropriate type)
- [ ] Set `scriptType` to "nodeflow.script.interpreter.js"
- [ ] Create placeholder for `startNodeID` (will set in Step 3)
- [ ] Set `stopNodeID` to "SuccessStopNode" or another terminal identifier
- [ ] Initialize empty `nodes` array

### Step 2: Plan the Flow Logic
- [ ] Map out the call flow on paper or diagram
- [ ] Identify all decision points (menus, inputs)
- [ ] Identify all prompts/messages needed
- [ ] Determine variable names for storing user input
- [ ] Plan error handling paths
- [ ] Plan hangup handling paths
- [ ] Determine where loops/retries are needed

### Step 3: Create the Start Node (ScriptNode)

## Troubleshooting

### Issue: Flow doesn't start when deployed
**Check:**
- Verify `startNodeID` exactly matches a node `id` in the `nodes` array (case-sensitive, exact UUID match)
- Verify the start node has a default event (empty name "") with a valid transition
- Verify `scriptType` is set to "nodeflow.script.interpreter.js"
- Check platform logs for initialization errors

### Issue: Call drops unexpectedly at a specific node
**Check:**
- Verify the node has all required attributes for its type
- Check if `isConfigruationsValid` is `true` for that node
- Verify all event transitions point to valid node IDs
- Check if any event has a null `unconditionalTransition` where it shouldn't
- Review platform execution logs for the specific call

### Issue: Digit collection not working / always timing out
**Check:**
- Verify `timeout` is set to a reasonable value (10000 ms = 10 seconds is typical)
- Verify `minDigits` and `maxDigits` are set correctly
- Check if `validInputExpression` is too restrictive
- Verify `promptName` is playing (audio file exists and is correct)
- Check if retry logic is configured (retries > 0)

### Issue: Invalid input loop never exits
**Check:**
- Verify `retries` attribute is set to a positive number (e.g., 3)
- Verify "max.retry.attempts.exceeded" event exists and transitions to a handler
- Check if "invalid.input.collect.digit" is looping back to the same node correctly
- Ensure retry counter is being incremented (platform should handle this automatically)

### Issue: Conditional transitions not routing correctly
**Check:**
- Verify expressions are valid JavaScript syntax
- Verify variable names in expressions match the `outputVariable` name exactly
- Ensure variables are declared before use (in initial ScriptNode)
- Check expression logic (e.g., "languageInput == '1'" not "languageInput == 1")
- Remember: expressions are evaluated in order; first match wins
- Verify `unconditionalTransition` serves as fallback if no conditions match

### Issue: Prompt doesn't play / silence instead
**Check:**
- Verify the audio file name in `promptName` exactly matches uploaded file name
- Verify file is uploaded to the platform's audio library
- Check file format is supported (typically .wav or .mp3)
- Verify `dataProviderType` is set to "play.prompt.annc.node.data.provider"
- Check if `timeout` is too short (file is longer than timeout)

### Issue: Script errors in ScriptNode
**Check:**
- Review `scriptErrors` array for specific error messages
- Verify all JavaScript syntax is correct (semicolons, braces, etc.)
- Check for undefined variables (declare before use)
- Verify `env` object methods are called correctly (e.g., `env.info()`)
- Wrap code in try/catch blocks to handle runtime errors gracefully
- Check for typos in variable names

### Issue: Hangup events not triggering
**Check:**
- Verify "hungup.collect.digit" (or similar) event exists for the node
- Verify it has a valid `unconditionalTransition` to a hangup handler
- Check if the event's `visible` flag is set to `true` (should be for explicit routing)
- Verify the hangup handler node exists and has valid transitions

### Issue: System errors keep firing
**Check:**
- Review platform logs for root cause of errors
- Verify all node configurations are valid (`isConfigruationsValid: true`)
- Check for missing required attributes
- Verify external dependencies (audio files, phone numbers, API endpoints) are available
- Ensure "system.error" event has `defaultFailureTransition: true` and valid transition

### Issue: Flow doesn't stop / continues after expected end
**Check:**
- Verify terminal nodes eventually transition to the `stopNodeID`
- Check if `stopNodeID` is set correctly in `nodeflowInfo`
- Ensure no accidental infinite loops (node transitioning to itself without exit condition)
- Verify success paths reach a StopNode or terminal state

### Issue: Child nodeflow invocation fails
**Check:**
- Verify child nodeflow ID is in parent's `connectedChildNodeflowId` array
- Verify child nodeflow exists and is deployed
- Check for circular references (parent invoking child that invokes parent)
- Review parameter passing (if applicable)

### Issue: Variables are undefined or have wrong values
**Check:**
- Verify variables are declared in an initial ScriptNode before use
- Check spelling of variable names (case-sensitive)
- Verify `outputVariable` attribute matches variable name in expressions
- Check if variable is being overwritten unexpectedly in a script
- Use `env.info()` to log variable values for debugging

### Issue: Timeout happens too quickly / too slowly
**Check:**
- Verify `timeout` values are in milliseconds (10000 = 10 seconds)
- Check if timeout is appropriate for the action (playback length, user think time)
- Ensure timeout is longer than the longest prompt that plays
- For DigitCollectionNode, timeout is for first digit (inter-digit timeout is platform-managed)

### Issue: Transfer doesn't work
**Check:**
- Verify destination number is in correct format (E.164 recommended: +1234567890)
- Check if number is reachable from the platform
- Verify caller ID is set appropriately (if required)
- Review transfer type settings (blind vs. attended)
- Check platform logs for transfer failure reasons

### Issue: JSON validation fails
**Check:**
- Run JSON through a validator (e.g., jsonlint.com)
- Look for syntax errors: missing commas, extra commas, unmatched braces/brackets
- Verify all string values are in quotes
- Check for illegal characters or incorrect escape sequences
- Ensure all UUIDs are properly formatted

### Issue: Nodes not appearing in visual editor
**Check:**
- Verify node's `visible` flag is `true` in `uiProps`
- Check if `x` and `y` coordinates are within the canvas bounds
- Verify `rendererType` is set to a recognized value (usually "DefaultNode")
- Check platform editor for zoom/pan settings
